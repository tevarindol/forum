# 0001. Не зберігати персональні дані користувачів

* Status: accepted
* Deciders: автор проєкту (курсова робота)
* Date: 2026-10-06

## Контекст і проблема

Чи варто зберігати email чи номер телефону користувача форуму? Зберігання полегшує відновлення пароля, але наражає користувачів на витік особистої інформації у разі зламу бази даних. Якщо ж персональні дані не зберігати, користувачеві практично неможливо відновити вхід у разі втрати пароля — і цю проблему доведеться вирішувати в майбутньому.

## Рушії рішення

* Безпека користувачів: зламана база не має видавати нічого особистого.
* Специфікація прямо забороняє email, ім'я та телефон у моделі.
* Проєкт навчальний, супровід релізної інфраструктури для захисту PII недоцільний.
* Компроміс уже знайдено: `username` зручний для входу й публічної ідентифікації.

## Розглянуті варіанти

* Зберігати email і/або телефон для відновлення доступу.
* Не зберігати персональні дані: ідентифікація лише через `username`, пароль — тільки `password_hash`.

## Результат рішення

Chosen option: «Не зберігати персональні дані», тому що модель не містить PII (критерії прийняття spec.md), а користувач ідентифікується лише `username`; пароль зберігається виключно як `password_hash`.

### Позитивні наслідки

* Витік бази даних не розкриває ні email, ні телефон, ні справжніх імен.
* Модель простіша: менше полів, менше обов'язків щодо їх захисту.
* Збереження лише хеша пароля відповідає безпеці навіть при витоку.

### Негативні наслідки

* Відновлення входу при втраті пароля майже неможливе — проблема на майбутнє (наприклад, через модерацію або наступні рішення).
* Нікнейм як компроміс може ускладнити взаємодію для частини користувачів.

## Плюси й мінуси варіантів

### Зберігати email/телефон

* Good, because користувач легко відновлює пароль автоматично.
* Bad, because при зламі бази назовні витікає особиста інформація конкретних користувачів.
* Bad, because порушує критерії прийняття специфікації.

### Не зберігати персональні дані

* Good, because анонімність за замовчуванням; витік бази мінімально шкодить людям.
* Good, because відповідає spec.md і літері критеріїв прийняття.
* Bad, because відновлення доступу потребуватиме окремого майбутнього рішення.

## Додаткова інформація

Застосовується в ER-моделі: `USER` містить лише `username` і `password_hash`; атрибути email/ім'я/телефон відсутні.
